# Практическая № 10 — командная работа в GitHub

Пять заданий на примере учебного интернет-магазина на Python.

Работа выполнена индивидуально в GitHub. Изменения после начального
коммита проходили через PR. На `main` включены защита и проверка Tests,
в том числе для администратора. Замечания в PR оформлены как
самопроверка. Одобрение второго человека в индивидуальной работе
отсутствует.

## Запуск магазина

Требуется Python 3.12 или новее. Установи зависимости в виртуальное окружение.

```sh
python -m pip install -r requirements-ci.txt
python -m pip install --no-deps --no-build-isolation .
python -m seminar_shop
```

## 1. Проверка email при оформлении заказа

`POST /orders/checkout` принимает цену в копейках, количество и email покупателя.

```sh
curl -sS -H 'Content-Type: application/json' \
  -d '{"unit_price":199,"quantity":2,"email":"shopper@example.com"}' \
  http://127.0.0.1:8080/orders/checkout
```

Ожидаемый ответ — `{"total":398,"email":"shopper@example.com"}`.

При пустом email API возвращает HTTP 400 и `Email is required`. При адресе
вроде `shopper` ответ тоже HTTP 400 с примером корректного адреса.
Пробелы по краям корректного адреса убираются.

```sh
python -m pytest tests/test_checkout.py -q
```

## 2. Сборка и проверки

Workflow **Shop CI** запускается для PR в `main` и после push в `main`. Теги
публикуются отдельно. Build собирает wheel, Lint показывает вывод Ruff и mypy,
Tests выполняет pytest, Package проверяет установку wheel и публикует
`shop-package`. Тесты запускаются независимо от линтера. XML-отчёты
`test-reports` загружаются и при падении тестов. Ключ кэша pip учитывает
версию Python и файл зависимостей.

## 4. Конфликт при слиянии

Две ветки меняли одну строку `MAX_ORDER_QUANTITY`: с 20 на 10 и с 20 на 25.
После первого PR вторая ветка конфликтовала в `src/seminar_shop/config.py`.
В обеих копиях второй ветки выбрано итоговое значение **15**. Тесты
прошли, а `git diff` между итоговыми деревьями не показал различий.

- **Merge.** Сохранились обе истории. Появился коммит с двумя родителями.
  Для его отката нужно указать основного родителя, например
  `git revert -m 1 <коммит>`, предварительно проверив порядок родителей.
- **Rebase.** Изменение второй ветки перенеслось поверх новой базы
  и получило новый SHA. История прямолинейная. Обычный коммит можно
  откатить командой `git revert <коммит>`.

Для рабочего PR выбран merge: так в истории видно исходное предложение
и отдельный момент разрешения конфликта.

## 5. Сканирование, staging и работа с Issue

Semgrep проверяет исходный код и сохраняет `semgrep-report` в Actions.
Два учебных правила ищут прямое использование `eval` и `exec`.

**Staging** запускается вручную из Actions с ветки `main`. Сначала
этот же коммит проходит Shop CI. При успехе запускается контейнер
из проверенного wheel и запрашивается `/health`. `API_TOKEN` задаётся
как секрет окружения `staging`. В логи значение не выводится.
На стандартном runner GitHub локальный адрес
`http://127.0.0.1:18080/health` доступен во время запуска, а после
завершения runner удаляется. Для постоянного стенда на отдельном runner
используются переменные `STAGING_RUNNER`, `STAGING_PORT` и `STAGING_URL`.

**Issue triage** обрабатывает новые Issues, назначает владельца,
добавляет `tech-debt` при отсутствии меток и назначает учебный milestone.
Дедлайн берётся из milestone и записывается в комментарий к Issue.
Для автоматической записи даты в GitHub Projects нужны переменные
`SEMINAR_PROJECT_ID`, `SEMINAR_DUE_FIELD_ID` и отдельный секрет
`PROJECT_TOKEN` с правом записи в этот проект.
